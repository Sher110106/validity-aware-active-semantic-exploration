## 1. The plan being pursued

Source: `IMPLEMENTATION_PLAN.md` (project root). Goal: replicate the "Active Semantic Perception" (ASP) paper — repo `grasp-lyrl/active_semantic_perception`, pinned commit `f1ea141b1886d33ab8f4e4b791db4d3c92150b27` — then add and evaluate a proposed validator/calibration/risk-sensitive-scoring extension. All heavy installs/builds/runs were required to happen on `tyrone` (RTX A6000 49GB, 112 cores, 125GB RAM, Ubuntu 24.04), never the local Mac.

Phase structure (§0-17 of `IMPLEMENTATION_PLAN.md`):

| Phase | What it is |
|---|---|
| 0-1 | Prerequisites, environment decision, checkout |
| 2-3 | Build (catkin workspace, Python env) |
| 4 | Dataset/config (HM3D scenes) |
| 5 | First official-policy run, 7-item success gate |
| 6 | Independent evaluator (object matching, GED, F1) |
| 7 | Replication matrix (4 scenes × 3 seeds, escalation ladder) |
| 8 | Validator + calibration + risk-sensitive scoring (the research contribution) |
| 9-13 | Extension experiments, ablations, final evaluation |

The plan states directly: the first successful run must use the official ASP policy before any validator/scoring code is added, and the full matrix should only be attempted after a one-scene baseline is reproducible ("don't skip rungs," §15).

## 2. How closely the plan was followed, and every departure from a pure replication

Phase order was respected (0→1→2→3→4→5→6, offline-8 built in parallel since it's Habitat/ROS-independent). Phase 7's full matrix was never attempted, correctly, because its precondition — a reproducible one-scene baseline — was not yet satisfied (see §5.3).

This is **not** a pure, unmodified replication. Three things depart from that:

1. **LLM backend swap (major, user-directed).** The author's pinned backend (Gemini pro-tier) became unusable mid-project: the exact model was deprecated, its replacement had no billing enabled on the available key, and every fallback flash-tier model either 503'd or hit a daily free-tier cap. The user was presented this as a decision only they could make and explicitly chose to switch to OpenRouter's `deepseek/deepseek-v4.1-flash`. This changes what the project can claim: it is now **a reimplementation of ASP's method on a different backend, not a replication of ASP's own numbers.**
2. **A change to pinned research code.** `exploration/scripts/llm_completion.py`'s `parse_response()` had no null-check on a regex match; one malformed LLM response crashed the entire 8-worker completion batch, discarding every other worker's already-good result. This was routed through the Opus advisor before touching it (see §4) and the change actually made is: on a regex-match failure, drop only that one ensemble member (log the raw response for audit) instead of raising; if literally every member in a batch fails, the original all-fail behavior (return `None`, let the outer retry fire) is preserved unchanged. On every input that already parsed correctly, the code is byte-identical to before. This is a real deviation from the pinned commit and is disclosed as such, not just logged in a bug list — the diff is saved at `runs/environment/llm_completion_parse_failure_fix.patch` on tyrone, with the original preserved at `llm_completion.py.orig_f1ea141` for a one-line revert.
3. **A brief, reverted deviation.** Two of the four target scenes were swapped out early in the session over a mistaken belief that the evaluator needed official HM3D semantic annotations. This was wrong and was reverted the same session after reading the author's own scoring scripts, which showed the evaluator's ground truth is self-generated by exhaustive exploration, not sourced from HM3D at all. No lasting effect, but it did cost time and is worth recording as a lesson: check what a evaluator's "ground truth" is actually sourced from before treating a missing-data gap as blocking.

Everything else — Docker-instead-of-native-Linux, the six infrastructure fixes in §3.5, the OpenRouter shim itself — is scaffolding around the pinned code, not a change to it.

## 3. Chronological account

### 3.1 Environment build (Phases 0-4)
tyrone runs Ubuntu 24.04, which has no native ROS Noetic packages, so a Docker image was built instead (`asp-noetic:latest`: Ubuntu 20.04 + ROS Noetic + CUDA 11.8). Full catkin workspace builds clean (30/30 packages). One real segfault was root-caused and fixed: `GTSAM_BUILD_WITH_MARCH_NATIVE=ON` gave two packages (`spark_dsg`, `hydra_ros`) different ABIs for the same struct (proven with a `sizeof`/`alignof` probe: 416/16 vs 448/32 bytes) — fixed by rebuilding GTSAM with that flag off. All four HM3D scenes are downloaded and correctly registered (see §2.3 for the swap-and-revert).

### 3.2 Phase 5 — official-policy gate-pass run
All 7 gate items (real scene graph populated, viewpoint selected, zero exceptions, replayable artifacts) passed **once, on the Gemini backend**, on scene 00069/seed 42. **This has not been re-verified on the current (DeepSeek/OpenRouter) backend** — the only evidence on the new backend is the partial, single-stage run in §5.1. That gap is real and open, not resolved by anything in this report; closing it (a full, clean multi-stage run reaching the gate's own checkpoints on the new backend) is the most direct next step (§7).

The backend forced the switch (§2.1). The sequence: `gemini-2.5-pro` (pinned) deprecated → replacement 429'd (no billing on the key) → `gemini-3.8-flash` 503'd on real workload → `gemini-2.5-flash` hit its daily free-tier cap (20 req/day) → user explicitly chose OpenRouter. A full translation shim (`tools/llm_openrouter/_asp_openrouter_shim.py`) intercepts calls at the same point an existing LLM-logging shim already patched, so `llm_completion.py` never knows a swap happened for calls that don't touch the parse-failure edge case in §2.2.

### 3.3 Ground-truth reference graph generation
The plan never budgets compute/API cost for generating each scene's ground-truth reference graph, since it's self-generated by exhaustive exploration, not sourced from HM3D (§2.3). `exploration/scripts/frontier_baseline.py` is a fully LLM-free exploration policy that terminates naturally on exhaustive coverage — running it closes this gap at zero API cost. Run on scene 00069 to completion: **52.8 minutes, 96.53m path, 26 stages, terminal graph of 67 objects / 9 rooms.** This is the ground truth used for the score in §5.1. The other three target scenes (00573, 00853, 00871) do not yet have reference graphs; the method to generate them is proven and unused so far.

### 3.4 Phase 6 (evaluator) and offline Phase 8
`tools/evaluator/` (object matching by geometric threshold — 0.5m objects / 4m rooms, graph edit distance with insertion/deletion cost 1 and forbidding-penalty substitution, precision/recall/F1) reproduces the author's own comparison rules from `ged_score_plot.py`/`f1_score_plot.py`. 9 unit tests pass. Until this session it had only been exercised against synthetic fixtures and mechanically against Phase 5 output shapes; §5.1 is its first real scored comparison.

`tools/asp_offline/` (Mac-side, ROS/Habitat/LLM-independent) implements the validator, leave-one-scene-out isotonic calibration, and risk-sensitive scoring per `IMPLEMENTATION_RESEARCH.md` §4.1-4.5. 13 unit tests pass, including two structural tests worth naming specifically:
- `test_validator_functions_never_take_a_reference_graph` — uses `inspect.signature` to fail automatically if a reference/ground-truth-shaped parameter is ever added to the validator's online decision functions. This enforces `IMPLEMENTATION_RESEARCH.md` §4.1's own stated constraint verbatim: "[validator constraints use] only the partial observed graph and fixed geometric rules — never hidden ground truth... this last only for post-hoc analysis, not for decisions." This was the spec's own requirement, not an invented one, and it was violated once by an earlier draft (a genuine `NameError` bug: `reference_graph` was referenced but never passed in) — fixed by removing all reference-graph access from the decision path and adding a separate, explicitly-labeled `label_against_reference()` post-hoc-only function.
- `test_held_out_scene_never_tunes_its_own_calibrator` — checks the leave-one-scene-out fold discipline directly with adversarial fixtures (samples constructed so a leaked fold would produce a visibly different, wrong calibrator).

Separately, `lambda_distance`'s default was an invented `1.0`; corrected to the author's actual `MOVE_COST_LAMBDA=0.2` after checking `pipeline_config.yaml` on tyrone.

### 3.5 Infrastructure debugging (the bulk of today's session)
Getting one clean, multi-stage LLM-policy run required finding and fixing problems across two honest categories — genuine bugs, and self-inflicted process failures along the way. Listing both plainly rather than inflating a bug count:

**Real bugs fixed (4):**
1. **OpenRouter provider-routing** — real (image+tool) calls failed 100% of the time under concurrent load because OpenRouter routed some requests to a backing provider that mishandled the combination. Fixed with `require_parameters: true` (OpenRouter's documented mechanism for excluding providers that don't support every field in a request).
2. **The pinned-code crash** described in §2.2.
3. **The shim's own retry loop didn't cover connection-level exceptions** — a raw `requests.ConnectionError`/`ReadTimeout` bypassed the retry mechanism built for exactly this kind of transient failure. Fixed by wrapping the call in `try/except` inside the existing retry loop.
4. **This container has no working outbound IPv6 route.** `curl -6 openrouter.ai` fails instantly (`HTTP 000`); `curl -4` succeeds in ~0.08s every time. `openrouter.ai`'s DNS intermittently returns an IPv6 address, and plain `requests`/`urllib3` has no dual-stack fallback, so a fraction of every call batch hung on a route that was never going to work. Fixed by monkeypatching `urllib3.util.connection.allowed_gai_family` to force IPv4. Verified: 5/5 consecutive test calls went from "some fraction hang for the full 180s timeout" to "all succeed in ~0.06-0.08s."

**Self-inflicted process failures, not new bugs (2):**
- **A regression, not a fifth bug.** Fix #1's `require_parameters: true` was paired with a hard single-provider pin (`"order": ["Together"]`). Under real sustained load that pin caused *that specific provider's own* rate limits to trigger. The fix: removed only the hard `order` pin; `require_parameters: true` — the part that actually fixes bug #1 — was never touched and stayed active throughout. So the original bug did not come back when the pin was loosened; only its over-correction was undone.
- **A silently-failed deployment.** Fix #3's edited file was `scp`'d to tyrone, and the deploy *looked* successful (unit tests reported 8/8 passing), but the host file had not actually been overwritten — almost certainly a casualty of this session's own SSH instability. The existing test suite doesn't cover the specific retry-on-exception behavior, so it passed against the stale, unfixed file and gave false confidence. Caught by chance during unrelated recovery work, not by the tests. **Process change adopted from this point on:** every subsequent deploy is verified with `diff` against the local source immediately after `scp` (not just "the command didn't error"), then `grep`'d directly in each deployed location after `docker cp`, before trusting a test run.

**One environmental cleanup, not a code bug:** a stale X11 lock file (surviving a container restart-after-host-reboot; `/tmp` isn't wiped by `docker start`) caused one launch attempt to crash immediately on the `pynput` keyboard-listener import. Cleaned up, moved to a fresh display number.

**Outside anything fixable from this session:** `tyrone` itself rebooted **5 times in roughly 2 days** during this work, unrelated to this project, each one killing the Docker container mid-run. This is very likely the actual explanation for the "severely unstable SSH" pattern noted earlier in the session (which had no identified cause at the time) and is flagged directly to the user as worth checking with whoever administers that machine. **A concrete risk this creates**: `DEVIATIONS.md`, described above as "the authoritative technical log," currently exists only on tyrone — a machine that has now rebooted 5 times in 2 days. It should be mirrored somewhere durable; this has not been done yet.

## 5. Actual results obtained

### 5.1 The one real evaluator score obtained so far

Run: `scene00069_seed42_v4`, OpenRouter/DeepSeek backend, official ASP policy, all four bug fixes from §3.5 in place. Scored via `tools/evaluator/evaluate_run.py` against the 67-object/9-room ground truth from §3.3.

**What `graph0`/`graph1` mean, since this needs stating explicitly:** the pipeline maintains two parallel scene-graph estimates simultaneously at every navigation stage (`graph0_dsg.json`/`graph1_dsg.json` from two independent tracks in the mapping backend), each completed and scored independently, then averaged. "Stage" is the navigation checkpoint (0, 1, 2, ...); `graph0`/`graph1` are two predictions produced *within* a single stage. The table below is entirely **stage 0** — the very first checkpoint, before any movement. Stage 1 exists with real scene-graph output but was excluded from scoring because its `navigation_stats.json` (written only on full stage completion) hadn't been written yet when the run was stopped.

| Graph | Precision | Recall | F1 | True positives | False positives | False negatives | GED | GED (normalized) |
|---|---|---|---|---|---|---|---|---|
| graph0 | 1.000 | 0.0299 | 0.058 | 2 | 0 | 65 | 161.0 | 1.059 |
| graph1 | 1.000 | 0.0149 | 0.029 | 1 | 0 | 66 | 167.0 | 1.099 |
| **averaged** | **1.000** | **0.0224** | **0.044** | — | — | — | **164.0** | **1.079** |

**What this means, stated carefully:**
- **Precision = 1.000** on 2 (and 1) matched objects respectively. This is consistent with correct behavior, but three total matched objects is far too small a sample to call this "validating" the pipeline or the evaluator — it is only a direction-of-travel check, not evidence of correctness at scale.
- **Recall ≈ 2%** (2-3 of 67 reference objects found) at the very first checkpoint, against a *fully exhaustive* 26-stage reference. Low recall here is the expected shape for an early single stage — but this report does not have enough evidence to rule out a rival explanation: that the object-matching geometric threshold (0.5m) is too strict, or that the pipeline is genuinely under-detecting objects it should have found in a full 360° initial scan. Distinguishing "expected early-stage gap" from "a real detection problem" requires at least one more stage of data, which this run did not produce before being stopped.
- **Normalized GED = 1.079** — the normalizer is `GED / (reference_nodes + reference_edges)` = `164 / (76+76)`. GED here counts node/edge insertions and deletions (substitution is free only for a near-exact match, otherwise forbiddingly expensive, per `ged.py`'s cost function, which mirrors the author's own `ged_score_plot.py`). A value above 1 is arithmetically expected, not a signal in itself: with the predicted graph nearly empty (2 nodes) against a 76-node/76-edge reference, transforming one into the other costs close to "insert almost everything," which is by construction close to the reference's own total size — and can exceed it slightly given a couple of non-matching predicted nodes that also need deleting. This number is a restatement of the same 2% recall already reported above, not an independent finding.

**To reproduce this score:** `python3 tools/evaluator/evaluate_run.py --run runs/scene00069_seed42_v4/stages --gt runs/scene00069_frontier_reference/stages/25/habitat_scene_graph_original_graph0.yaml --out eval_results.json`, run inside the container's Python environment (`source /workspace/environments/semantic_perception/bin/activate` first). Full output saved at `runs/scene00069_seed42_v4/eval_results.json` on tyrone.

## 11. Follow-up: full paper audit and a "maximum settings" experiment, with a negative result (2026-09-14)

Per explicit user request ("go through the whole paper and see what we missed," "miss no issues," "use DeepSeek's max settings"), the replication was systematically audited against the full published paper (arXiv:2510.05430v2, read end-to-end including footnotes) and DeepSeek's reasoning effort was raised to its maximum ("high") setting for a real, bounded run. Full evidence trail: `DEVIATIONS.md` entries #51-55 on tyrone.

**Audit findings.** All tunable parameters were confirmed matching the paper, with no fix needed: room weight λr=1 and move-cost λd=0.2 (paper) match `UNCERTAINTY_ROOM_WEIGHT`/`MOVE_COST_LAMBDA` in `pipeline_config.yaml`; the paper's m=4 completions × 2 scene graphs = 8 samples matches `LLM_ENSEMBLE_COUNT`/`SCENE_GRAPH_COUNT`; 300 candidate viewpoints matches `UNCERTAINTY_SAMPLES`. Two gaps were confirmed genuinely unfixable rather than guessed at:

- **F1 category restriction.** The paper scores F1 only over an unpublished "61 common indoor object categories" list. Searched exhaustively — the full paper text and every footnote, the pinned repo at its confirmed-true HEAD, the GitHub repo's README and Issues (empty, no discussions exist), and general web search for author blogs or project pages — and found the list nowhere publicly accessible. This project's evaluator scores every category; documented as a permanent, disclosed limitation, not invented.
- **Ground-truth generation driver.** The paper uses a human manually piloting the camera for exhaustive coverage; this project uses an automated frontier-exploration policy instead. Confirmed both produce the same file format via the same underlying conversion mechanism — only the driver differs. Reasoned through the direction of any resulting bias: a less-thorough automated policy would shrink the ground-truth object count, which would inflate (not deflate) measured recall — the opposite of the observed gap — so this is unlikely to explain it. Disclosed regardless.

**The reasoning-effort experiment.** DeepSeek's reasoning effort was raised from "low" to "high" (the maximum available setting), re-tested in isolation first given "high" was the original cause of a 100%-empty-completion failure earlier in the session — the isolated re-test showed that failure no longer reproduces, attributed to earlier provider-routing fixes rather than anything inherent to "high" itself. Deployed, then load-tested for real: under sustained 8-worker concurrent load, ~10% of calls still hit the token-length ceiling even at "high" effort's original 16,000-token budget; raised to 24,000, which eliminated the issue.

A full run (`scene00069_seed42_25m_20260914_high_effort_v5`) was then launched with a properly-sized call budget (1,500 calls) and a `sed`-based launcher script written specifically to avoid a `BASE_DIRECTORY`-staleness mistake made during an earlier, smaller test of "high" effort (that mistake cost no data — the run's real output was found intact at the old path via file timestamps — but the fix was applied going forward). The run reached 7 complete navigation checkpoints out to 30.5 m of path (v3's "low effort" run reached 25.275 m in 5 checkpoints), using only 412 of its 1,500-call budget. No crashes, no cap exhaustion; the pipeline has no automatic path-budget stop condition, so it was stopped manually once it had clearly passed v3's endpoint.

The finding survives the correction and is if anything sharper: high effort still loses on F1 under both comparisons (a larger gap than the mislabeled table showed), and GED is genuinely worse too (1.189 vs. 1.075) — the mislabeled table had GED backwards, showing v5 as better, an artifact of comparing the wrong graphs. Precision is close between the two runs (~0.66–0.67) — most of the real gap is recall, as originally stated below, though the exact magnitude changes with the correction.

**Root cause, confirmed by direct log comparison, not guessed.** Grepped "ensemble members were dropped" across both runs' full pipeline logs. v3 (low effort) averaged 2.0 of 8 ensemble completions dropped per round (75% survival). v5 (high effort) averaged 3.33 of 8 dropped per round (58% survival) — one round lost 7 of 8 entirely. "High" reasoning effort makes DeepSeek more likely to wrap its YAML output in markdown code fences or otherwise deviate from the bare-YAML format the pipeline's parser requires, so the existing per-worker drop guard (§3.5's resilience fix) discards more completions before they can contribute any predictions. Fewer surviving completions per round means less object coverage in the merged graph, which drags recall — and therefore F1 — down, despite the model spending far more reasoning tokens per call.

**Against the paper's own numbers.** The paper's Fig. 4 table gives its own scene-69 trajectory ("Semantic (Ours)"): F1 = 25.8% at 10% of its own exploration budget, 60.1% at 50%, 62.2% at 100%. ~~Both of this project's runs (35.7% best case)~~ Both of this project's runs (35.2% best case, corrected) sit between the paper's 10%-budget and 50%-budget checkpoints — meaningfully behind a fully-scaled run, consistent with the two disclosed, unresolved gaps above (unpublished category list, DeepSeek Flash vs. Gemini Pro capability tier) rather than anything newly found in this experiment. The paper doesn't state an absolute path length for its own 100% budget on scene 69, so the exact fraction our ~25–30 m represents isn't precisely known.

**Recommendation, not yet acted on:** revert the reasoning-effort default from "high" back to "low" for any future run on this pipeline — it costs more (calls, tokens, wall time) and measurably hurts the one thing it was meant to help. This is a finding specific to this pipeline's strict-YAML parsing architecture, not a general claim about reasoning-effort settings elsewhere.

## 12. Follow-up: independent review found and fixed two real bugs (2026-09-14)

An independent review (`REVIEW_2026-09-14.md`) audited this report, `IMPLEMENTATION_PLAN.md`, and the underlying code, and found two real correctness problems, both now fixed (full evidence: `DEVIATIONS.md` #56):

1. **The support-denominator bug** driving the extension ablation's support-threshold policy: it measured agreement as (hits) / (however many ensemble completions survived upstream parsing), not (hits) / (the pipeline's actual ensemble size, 4 per scene-track). This inflated support exactly on the stages with the most parsing failures. Consulted an Opus advisor on the exact fix before touching code behind already-published numbers, given the ambiguity in what "the ensemble size" even means for this pipeline's two-track architecture (resolved: 4 per track, not a pooled 8 — pooling would also have been wrong, since room ids aren't a shared namespace across graph0/graph1). Fixed, tested (2 new regression tests, 2 existing tests updated to keep their original intent), and redeployed; 30/30 offline tests and 10/10 evaluator tests pass live on tyrone. A side effect the advisor caught: under the old bug, tau=0.75 and tau=1.0 were frequently the identical policy due to a quantization artifact at low survival counts, which partly explains the "precision climbs monotonically with tau" pattern reported earlier in this project's work — the tau grid has been collapsed from 9 points to the 4 values (0, 0.5, 0.75, 1.0) actually reachable under a correct K=4 denominator.
2. **The "tracked graph" mislabel** in §11 above, corrected in place there — the numbers reported as the paper-comparable tracked-graph score were actually the ablation's own filtered/merged graph, computed with a different (non-author-faithful) matching algorithm than `tools/evaluator/`'s. The true tracked-graph numbers are now reported in §11's correction.

A third, smaller bug was found and fixed in passing: `tools/asp_offline/evaluator.py`'s GED computation didn't re-sort a predicted-edge tuple after mapping its endpoints into reference-id space, occasionally double-counting a real shared edge as a spurious insertion plus deletion. This affects only the offline extension's own internal ablation GED, never `tools/evaluator/`'s author-faithful GED (which uses networkx's real graph-edit-distance search directly on node attributes, with no manual ID-remapping step to get wrong).

Also addressed this pass, per the review's evidence-completeness and reproducibility findings: `tools/evaluator/` (previously on tyrone only, now mirrored and hash-verified identical) is the tool that actually produced every "comparable to the paper" number in this report, distinct from `tools/asp_offline/evaluator.py` (the extension's own internal, self-consistent-but-not-author-faithful evaluator, used only for comparing the four ablation policies against each other); v5's full run manifest, config, pipeline log, call counter, and deployed shim revision are now mirrored locally (previously only the two ablation JSONs were); and a new `tools/run_manifest.py` content-hashes every input a reported number depends on into one `run_manifest_hashes.json` per run.

**Not yet addressed**: tau=0.75 was selected by eye from a sweep scored against the only reference graph that exists, an in-sample selection the denominator fix doesn't resolve — every tau=0.75 number in this report remains an exploratory best-point-on-one-scene, not a held-out-validated choice, until reference graphs exist for the other three scenes.
