# Review of ASP Replication Direction and Next Steps

**Review date:** 2026-09-14
**Reviewed files:** IMPLEMENTATION_PLAN.md, SESSION_REPORT_2026-09-13.md, tyrone_mirror/DEVIATIONS.md entries #51-55, the mirrored v3/v5 result JSON, and the offline validator/evaluator code under tools/
**Verdict:** the project is moving in the right direction, but it is not ready to scale to the full experiment or claim model equivalence. The next work should repair evidence and metric discipline, generate the remaining reference graphs, then run a real calibrated and live policy comparison.

## Current position

The work has achieved a strong engineering milestone:

- The author's repository and commit are pinned.
- The ROS/Habitat stack was made runnable in a Docker ROS Noetic environment on tyrone.
- A real ABI mismatch was found and fixed.
- The parser crash and several infrastructure failures were identified and disclosed.
- Scene 00069 has an exhaustive frontier reference graph.
- The offline validator, evaluator adapter, calibration code, and tests exist.
- A real 25.275 m DeepSeek/OpenRouter probe completed without a worker crash.
- The v3 cache produced a coherent filtering signal: precision improved while recall stayed approximately flat.

That is the right sequence for a difficult reproduction. The team also made the correct decision to defer the full matrix after discovering that the current backend had not passed the original full gate.

The project has not yet reproduced the author's experiment in the strict sense. It is currently a substitute-backend reimplementation of the ASP method:

- The usable backend is DeepSeek V4.1 Flash through OpenRouter, not the author's Gemini Pro configuration.
- Only scene 00069 has a reference graph.
- Only seed 42 has been run.
- The current probes cover roughly 25 to 30 m, not the planned 120 m.
- The extension replay is a static analysis of cached completions. It does not yet change the navigation trajectory.
- The proposed calibrated policy has not been evaluated because there are not enough scene reference graphs.

The wording in the plan and report is mostly honest about these limits. Keep that framing.

## What the current results establish

The v3 run is useful evidence that the pipeline and data path are alive:

- Five navigation stages reached 25.275 m.
- The independent evaluator produced changing object metrics across checkpoints.
- The validator found interpretable failure modes in real completions.
- The filter-only and support-threshold controls improved precision on shared cached completions.
- The same replay produced the same result on the Mac mirror and on tyrone.

The v3 extension replay shows a useful diagnostic pattern. Its official raw-completion AUC is approximately precision 0.490 and F1 0.326. The combined uncalibrated support-threshold result at tau 0.75 is approximately precision 0.681 and F1 0.357, with recall approximately 0.245 in both cases. This supports the narrower statement that the proposed structural filtering and an uncalibrated agreement threshold can remove many false predictions in this one cached scene while retaining similar matched-object recall.

It does not yet establish that the filter improves exploration. The code that generated the replay explicitly says the LLM proposals are not merged into the tracked graph used by the live pipeline. Therefore the replay currently measures prediction quality under filtering, not path selection, false-positive detours, collision behavior, or room discovery caused by a different policy.

The high-effort run is also useful, but its conclusion must be scoped carefully. The measured configuration was:

- DeepSeek high reasoning effort.
- A larger max-token ceiling than the low-effort v3 run.
- OpenRouter provider routing under a different load pattern.
- A different set of surviving completions.
- A different path endpoint and a different number of checkpoints.

It is valid to report that the observed high-effort configuration performed worse than the observed low-effort configuration on this pipeline. It is not yet a clean causal experiment proving that the single variable reasoning effort caused the full F1 difference. The log evidence gives a strong mechanism candidate: high effort produced more unparsable responses, so fewer ensemble members survived. That mechanism should be measured directly in the next controlled comparison.

## Model comparison: Gemini Pro versus DeepSeek Flash

The current evidence does not support the claim that Gemini 2.5 Pro Preview and DeepSeek V4.1 Flash are on par.

It supports a narrower claim:

> DeepSeek V4.1 Flash is usable as a substitute backend for exercising the ASP workflow, and it produced complete bounded runs after the routing and resilience fixes.

There is no paired head-to-head result in the current artifacts where both models receive the same captured prompt, image inputs, tool schema, and checkpoint and are scored with the same parser and evaluator. The lower score against the paper may come from several sources:

- Different model capability.
- Different output-format compliance.
- More dropped ensemble members.
- The unpublished 61-category F1 restriction.
- Different ground-truth driver.
- The shorter path budget.
- Provider routing and rate-limit behavior.

The high-effort result particularly suggests a format-compliance problem, but that is not the same as a general reasoning-capability comparison. If old Gemini responses still exist on tyrone, mirror them and run a response-level comparison. If they do not exist, do not make a parity claim. Use the substitute-backend wording in the report.

## Findings that need action

### High priority: raw support uses the wrong denominator when completions are missing

The intended support is the fraction of K=8 completion samples containing a hypothesis. The current implementation in tools/asp_offline/calibration.py computes:

~~~~text
hits / len(completions)
~~~~

The replay removes missing or malformed files before passing the ensemble to match_hypotheses. Several real stages do not have eight completions:

- v3 stage 2 has 2 and 3 completion files for its two graph tracks.
- v3 stage 3 has 3 and 4.
- v3 stage 4 has 2 and 4.
- v5 has even fewer in some stages.

This means a hypothesis present in 2 of 2 surviving files receives support 1.0, even though only 2 of the intended 8 samples survived. That inflates support precisely on the stages with more parsing failures and makes tau results incomparable across stages. It also makes the support-threshold policy different from the research definition.

Fix this before treating any support result as meaningful:

1. Carry expected ensemble size explicitly, default 8.
2. Count dropped/missing members as non-hits.
3. Compute support as hits / 8.
4. Record available count, missing count, and denominator in every output.
5. Add a test where two of eight files survive and verify support is 0.25, not 1.0.

If the author pipeline's 8 samples are represented as two groups of four, preserve that structure and document whether support is computed over all eight or per graph track. The current code must not silently use the number of available files.

### High priority: v3 and v5 extension AUCs contain incomplete ensemble observations

The v3 and v5 extension replays are valuable diagnostics, but they are not eight-sample policy evaluations at every checkpoint. Some stage summaries are based on only one to four completion files per track. The JSON records completion counts, which is good, but the headline AUC should not be presented without the missingness rule.

After fixing the denominator, choose one preregistered policy:

- Exclude a checkpoint from the extension analysis unless all eight completions exist.
- Or include it with missing completions counted as failed/unparseable samples.
- Or report both complete-only and all-available analyses, with the latter explicitly marked sensitivity analysis.

The preferred option is to keep the full data with missing members counted as failures for validity-rate diagnostics, then report a complete-ensemble sensitivity analysis. Do not allow missingness to change the effective K.

### High priority: support threshold tau is currently tuned on the same reference used for scoring

The replay sweeps tau from 0 to 1 and the strongest-looking result is around 0.75. Because there is only one reference graph, any choice of tau based on that result is in-sample tuning against the evaluation reference.

Calling the policy UNCALIBRATED_PROVISIONAL is correct, but it does not remove the selection bias. Treat the current tau curve as exploratory. Before making a performance claim:

1. Generate references for 00573, 00853, and 00871.
2. Declare how tau will be selected using only calibration scenes.
3. Evaluate the selected tau on the held-out scene.
4. Keep the current 00069 curve as a transparent diagnostic, not as the final selected policy.

### High priority: the extension has not yet been tested as an exploration policy

The extension replay compares filtered graph predictions against a reference. It does not re-run viewpoint selection and navigation after validation, calibration, or risk scoring. As a result, it cannot measure the project's central decision-level outcomes:

- False-positive detours.
- Path length.
- Collisions.
- Unseen-room discovery.
- The risk term's effect on selected viewpoints.

The next live extension run must use the same cached completions and the same observed graph at each checkpoint, then run the candidate scoring and planner for each policy. At minimum, compare:

1. Official ASP scoring.
2. Validator-only scoring.
3. Calibrated-support scoring.
4. Combined calibrated-risk scoring.

The policies must use shared completions wherever possible. Save the selected candidate, score components, planned path, actual path, and fallback reason for every policy and checkpoint.

### Medium priority: the high-effort experiment needs a controlled token-budget ladder

The next intended experiment is to keep reasoning effort at high and increase the per-call token budget. This is a reasonable direction because the real concurrent run showed length-limit failures at 16,000 tokens, while the later 24,000-token run completed without that failure pattern. The earlier isolated 32,000- and 65,000-token checks did not show a quality gain, but they were not a substitute for a full multi-stage run under sustained eight-worker load.

The current high-versus-low result remains an exploratory configuration result, not a clean causal estimate. More than reasoning effort changed:

- The max-token ceiling changed from the earlier 16,000 setting to 24,000.
- The high-effort run used different path coverage and checkpoints.
- Provider routing can vary under concurrent load.
- The number of surviving completion files differs.
- The v5 raw pipeline log is not present in the local mirror.

Run the next high-effort trial as a new, fully logged configuration:

1. Use high reasoning effort with max_tokens=32,000 as the first higher-budget trial. Do not jump directly to 65,000 because the isolated test was much slower without a quality gain.
2. Keep the prompt, image inputs, tool schema, model identifier, provider constraints, scene 00069, seed 42, sensor configuration, candidate-view seeds, and launch script identical to v5.
3. Keep the same output parser and fail-soft behavior. Do not silently widen the parser during this trial, because that would mix a token-budget experiment with a parser experiment.
4. Use a fresh run directory and a total call cap large enough for the observed high-effort rate. The cap must terminate safely or be watched continuously because the pinned retry loop can spin after cap exhaustion.
5. Record per call: requested max_tokens, reasoning effort, provider route, finish reason, prompt tokens, completion tokens, latency, HTTP/provider errors, parse status, and output byte count.
6. Record per ensemble round: expected members, received members, parsed members, dropped members, drop reason, valid predicted nodes, removed nodes, and whether the round was complete.
7. Stop at the first checkpoint beyond the same 25 m endpoint used for v3/v5 comparison, with a watcher that stops the pipeline cleanly and restores the original configuration.
8. Compare high/24k versus high/32k first. Then compare both against low-effort v3 using the same endpoint and corrected metrics.

The 32,000-token trial passes its operational gate only if it has no uncontrolled cap loop, no stale output path, complete run metadata, and a measurable reduction in length-limit failures or dropped completions. It passes its quality gate only if the corrected fixed-K evaluation shows improved or preserved recall/F1 without an unacceptable cost increase. If 32,000 still produces no gain, stop increasing the token ceiling and keep the negative finding scoped to this backend and task.

The model claim remains separate. These runs can test whether more token budget makes DeepSeek more usable in this pipeline; they cannot establish that DeepSeek V4.1 Flash is on par with Gemini 2.5 Pro Preview without paired same-input evidence.

Also resolve the path mismatch between references to runs/environment/DEVIATIONS.md on tyrone and the local tyrone_mirror/DEVIATIONS.md. Every report should say clearly whether a path is on tyrone or in the local mirror.

### Medium priority: preserve the actual evaluator implementation

The report refers to tools/evaluator/ on tyrone, while the current workspace exposes tools/asp_offline/evaluator.py and tools/evaluate_cached_run.py. The actual evaluator used for some reported tracked-graph numbers is not visibly present in the local project.

Mirror the exact evaluator source that produced the v3 and v5 tracked-graph values. Add a manifest containing:

- Source path and commit or file hash.
- Ground-truth file hash.
- Input graph file hashes.
- Metric configuration.
- Output JSON hash.

This prevents the report from depending on code that exists only on tyrone.

### Medium priority: strengthen evaluator tests before using GED as a primary outcome

The local evaluator performs greedy label-and-distance node matching, then counts node and edge differences. It should be checked against the author's actual GED implementation rather than assumed equivalent.

Add tests for:

- Reversed edge endpoint order.
- Different predicted and reference identifier ordering.
- Duplicate labels at similar distances.
- One-to-one matching when three predictions compete for two references.
- A predicted room and object with mapped IDs whose lexical order reverses.
- Structure and nothing nodes being excluded.
- The exact reference-size normalizer.
- A case where a non-matching substitution has the author's intended penalty.

In particular, canonicalize mapped predicted edges before comparing them with reference edges. The current local code sorts raw reference edges but does not visibly sort the mapped predicted edge tuple after applying the node map. That can create a spurious edge edit when mapped endpoint identifiers reverse lexical order.

### Medium priority: correct the plan's completion wording

IMPLEMENTATION_PLAN.md currently marks the risk-score and ablation item as complete, but the actual replay is an uncalibrated support-threshold diagnostic and does not run the live risk-sensitive score. Mark that item partial until both conditions are true:

- A real calibrator has been fit under leave-one-scene-out.
- The calibrated risk score has changed candidate selection or has been evaluated in a live/replayed planner loop.

The plan already correctly marks the current-backend gate, the independent evaluator, calibration, the full matrix, and final guardrails as open or partial. Keep those statuses.

8. Mirror the complete raw output back into this workspace.

The substitute backend completed bounded scene-00069 probes after infrastructure and parser-resilience fixes. > On one scene and one seed, an offline replay of shared cached completions showed that structural validation and an uncalibrated support threshold increased precision while preserving approximate object recall. This is a prediction-quality diagnostic. A live decision-level comparison and held-out calibrated evaluation remain pending.

Use this wording for high effort:

> In an exploratory OpenRouter comparison, the deployed high-effort configuration had lower recall and F1 than the earlier low-effort configuration. The difference coincided with more malformed or dropped ensemble members. Because token budget, surviving samples, provider behavior, and path coverage also differed, the result is treated as a configuration finding rather than a clean causal estimate of reasoning effort.

## Final assessment

The project is on the right path. The environment work is sufficiently mature to stop debugging infrastructure as the main activity. The research work should now focus on three proof obligations:

1. Correct, fixed-denominator evaluation over complete and incomplete ensembles.
2. Real held-out calibration across four reference scenes.
3. A decision-level policy comparison in which validation and risk scoring actually affect viewpoint selection and navigation.

Until those are complete, the work is a well-documented and promising substitute-backend reimplementation with early diagnostic evidence. It is not yet a full ASP replication, a model-parity result, or evidence that the proposed policy improves exploration.
